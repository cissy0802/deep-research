## 1. Uvik SDD benchmark(M01–M10):厂商口径,本身也撑不起"spec 提升合并率"

- **设计**:50 张生产 Python 工单 × 5 臂(Spec Kit / Kiro / BMAD / OpenSpec / 无 spec),由人工评审决定是否合并。页面标「Last updated: October 8, 2026」,另一处摘要写 10-15。
- **合并率**:spec 各臂 80–84%(40–42/50),对照 72%(36/50)。**Uvik 自己写了合并率的噪声带是 ±10pp。**
- **本线复算(M03)**:最好的一臂(42 vs 36)Fisher p≈0.23,两组 95% CI 大面积重叠。按同工单配对算,6 个不一致对必须全部偏向 spec,McNemar p≈0.031 才显著。另外是 4 臂对 1 个对照,存在多重比较。**合并率差异在统计上不能和零区分。**
- **评审缺陷**:每合并工单 0.46(各臂 0.39–0.57)vs 0.86,这是最好看的数字,但有三个陷阱:
  - 分母是各臂各自的已合并集合,幸存者构成不同;
  - 缺陷是评审时记录的,不是上线后的缺陷;
  - 评审者能否从 PR 形态猜出臂别,未核。
- **代价**:spec 臂合并中位 36–55 分钟,对照 29 分钟。spec 阶段占 35.1% 的 token(BMAD >40%)。每合并工单成本:对照 $2.43,spec 臂 $2.35(Kiro)到 $4.23;Kiro 用 credit 计价,与其他臂的成本口径可能不可比。
- **异质性**:bug 修复、重构、写测试三类工单上 spec「不回本」。feature 和数据管线工单上最好一臂 90% vs 60%,但这是事后子组,n 未知。
- **唯一的类漂移数字(M08)**:spec 臂已合并工单中有 7.9% 的代码与自身 spec 不符。这是实现时点的一致性,不是随时间的漂移。
- **混杂与可复跑性(M09)**:
  - 模型一说 5 臂都用 claude-sonnet-5,一说 4 个框架里只有 3 个跑在 Claude Code 内(Kiro 疑在自有 IDE),即工具链(harness)和 spec 方法一起变;
  - 每臂运行次数始终没找到,按单次采样做假精度审计;
  - CSV(uvik-sdd-benchmark-2026-results.csv,CC BY)只有声明,没拿到下载链接,本线未能复跑。
- **谁在说话(M10)**:Uvik 是塔林的 Python 外包/人员增补公司(自称 2015 年成立、30+ 人),不卖 SDD 工具,但基准属于内容营销。「spec 略好、更贵更慢、小单不划算」的结论恰好支持「需要资深工程判断」的服务叙事。同一批 50 张工单还做过一个 agent 对比基准。没有任何独立团队复跑;mattbutlerengineering/ai-tooling 以「自报厂商基准」为由拒收。
- **可用的说法**:「一家外包公司的单轮自测中,spec 臂合并率高 8–12pp,但在其自报的 ±10pp 噪声带内;评审缺陷约少一半;时间与成本普遍更高;小型和修复类工单无收益。」

## 2. 单人/小团队实测(M11–M16):没有一条能承重

- **dimwiddle(DEV)**:1 个项目、2 种设置。真正的发现是 agent 自评不可靠、需要外部验证,这混淆了 spec(T1)与验收测试(T4)。
- **OrangeLoops**:外包商案例,无对照。195 个任务约 2 小时生成,随后**4 天稳定化**,两个数字必须同时引用。后端阶段用掉约 95% 上下文。
- **Medium OpenSpec vs Spec Kit**:单次运行,57.7k vs 121k、91.7k vs 181k token。方向与 OpenSpec README 自述「heavyweight」一致,量级不承重。
- **UCL × Microsoft 10 组实验**:同一工具只改提示写法,结果差异就很大。这条有用在于噪声口径:工具内方差这么大,跨工具的单次比较(Uvik)更难解读。「4h53m vs 2h24m」未能在原文定位,禁用。
- **levelup「spec 返工率」**:是度量提案,不是测量;全网未见任何人按此口径公布数据。
- **现场核验(M16)**:
  - Spec Kit 9 个命令模板共 128KB,specify+plan+tasks+implement 四个共 51KB,粗估约 1.3 万 token,调用对应命令时注入;
  - OpenSpec 12 个 skill 共 184KB;
  - SDD 工具本身就是大块指令上下文,直接连到 #14 的 context 成本口径;
  - spec-kit issue #1401「每会话 18.6k token」未能读原文,不采信。

## 3. 学术受控证据(M17–M24):"spec 细节有用"有支撑,但操纵的是题面信息量,不是 SDD 流程

最强的一组,方向一致:**降低规约完整度,结果单调变差;补回规约,结果恢复。**

- **Specification Gap**(51 题,L0→L3):单 agent 89%→56%,双 agent 58%→25%;补回完整 spec 即回到 89%。剂量-反应清晰,但单作者、合成任务。
- **SWE-Bench Pro 消融**:去掉 requirements+interface 后「显著退化」。二手数字 25.9→8.4,与公开集头条 23.3 对不上;作者承认部分来自测试名称假阴性;混合了 T1 与 T3。
- **Ambig-SWE**(ICLR 2026):欠规约输入上,交互澄清最多提升 74%;模型默认不提问,也分不清题面欠规约还是充分。
- **测试生成两篇(T3/T1)**:
  - Tufano(Google):半形式规约先行,检出率 +9.8pp、分支覆盖 +2.5pp,token +38%,即**有效但有税**;
  - Haeri(TD Bank):给规约 27/30,无规约 2/30;**题面本就充分时无增益**,这是关键边界条件。
- **WiseSpec**:需求打分-精炼环,+2–29pp;换强模型(Opus-4.8)只剩 +3pp;无组件消融、无等算力基线。
- **SDD 工具本身的评测**:
  - Spec Kit Agents:比较的是 Spec Kit+钩子 vs Spec Kit,LLM 评审分 +0.15,SWE-bench Lite +1.7pp;
  - SSDE:领域模型+Gherkin 的收益随模型和系统不稳定。
- **迁移陷阱**:这些研究都说明「信息够不够」重要,没有一篇证明「走 Spec Kit/Kiro 这类流程」优于「把需求写清楚的一段提示」。Uvik 的工单是生产工单,题面已有一定规约,按 Haeri 的边界,收益本就应该小。

## 4. 流程税、自欺与漂移(M25–M31)

- **Rebuild Dossier 空桩(逐字核对)**:一个什么都不做、只回 200 的 handler,通过了全部 spec 派生测试(可见 20/20、留出 12/12),77 项保真检查 0 项全匹配。**T4「测试全过」≠ spec 被满足。** 作者主动公布了这个对自己不利的结果。
- **同一来源**:弱模型读懂 CLAUDE.md 规则后照样违反;作者的应对是把规则改成 hook 强制执行。写进上下文的 spec ≠ 被执行的 spec。
- **Gated SDD 审计轨迹**:流程未要求的重复审查吃掉 75.3% 的审查 token;编排者自己运行并评判自己的检查。
- **spec-first convergence**:n=1,作者公司出品所用 agent,只能作可行性案例。
- **返工率**:唯一的大样本测量是 ESEM 2026 Hill(CON 线负责)。作者内对比返工 +1.2pp(p=0.001),方向与厂商主张相反;但样本中的 spec 工件是 ticket 引用,不是 SDD 工具产物。
- **漂移**:没有找到任何纵向的 spec 漂移测量。SpecMine(CMU)显示多数 spec PR 同时改代码,但没测随时间的漂移;其公开 PR 层(5,992 个 PR)可做本期现场核验,统计 spec 最后修改相对代码最后修改的滞后分布。
- **Tessl 自测**:约 35%、最高 3.3×/平均 1.17×(两个数必须并列)。所谓 usage spec 实为库文档上下文,机制属 #14,不属 SDD。

## 5. #14 / #0 已核口径的迁移(M32–M35,标「#14 已核」不重证)

| 口径 | 已核结论 | 迁移到 SDD 的方式 | 边界 |
|---|---|---|---|
| AGENTbench(2602.11988) | R3 否决 pp 级差值;只存活零效应、约 +20% 成本、agent 会遵从 | 常驻 spec/constitution/steering 文件作为上下文:有成本、无保证收益 | 操纵的是仓库级常驻文件,不是任务级 spec;不得当「SDD 无效」的证据 |
| Shepard & Albrecht(2606.20512) | 25.5→28.3→33.0%,迭代精炼显著 | 与 WiseSpec、Tufano 同向:**有效成分可能是带执行反馈的环,不是文档本身** | 指导文件含仓库地图;可能是算力效应 |
| context rot(Chroma + 独立文献) | 聚焦 vs 约 113k 干扰上下文,差 10–40+ 点 | 长 spec 栈(95% 上下文、单模板 8–22KB)有稀释风险 | spec 是相关上下文;没有直接测「spec 长度→结果」的研究 |
| METR RCT(#0) | −19%,自评 +20% | 从业者自报的「SDD 让我更快」不构成证据 | 只迁移方法学,不迁移效应量 |

## 最强 / 最弱证据

- **最强**:
  1. Specification Gap 与 SWE-Bench Pro 消融(受控操纵规约完整度,方向一致;待回一手);
  2. Rebuild Dossier 空桩基线(逐字、可复现、反利益);
  3. 本线对 Uvik 的复算(合并率差不显著,不依赖 Uvik 的叙述)。
- **最弱**:
  1. Uvik 子组「feature 90% vs 60%」及「≥3 文件才有益」;
  2. OrangeLoops「2 小时生成」(无对照、营销);
  3. Tessl 3.3×(厂商、机制错位)。
