# G23 — Lens K(口径)

**组判定:修正**(「spec 细节越完整,agent 结果越好」这个方向在四篇论文的一手中都成立。修正的是:M17 的退化有一部分是测量工具造成的;M21 把两个条件混成了一个;M22 的「2–29pp」混入了弱基线)

核验方式:从 arXiv 下载 PDF(2509.16941、2603.24284、2607.06636、2609.00568)并用 pdftotext 检索;四篇的数字都在原文表格或正文中定位到了。

- **M17 修正(升级为 verbatim + 测量口径)**:Table 3 原文:「OPENAI GPT-5 (HIGH) 25.9% → 8.40%;CLAUDE OPUS 4.1 22.7% → 8.20%」(PROBLEM STATEMENT, REQUIREMENTS, INTERFACE vs PROBLEM STATEMENT ONLY)。「25.9 与 23.3 不一致」已解决:Table 5 中 23.3 是 **GPT-5 (MEDIUM)**,25.9 是 GPT-5 (HIGH)。§6.2 原文:「Without the requirements and interface, both models… show significantly degraded performance… Since unit tests expect a narrow set of solutions, verifiers are prone to false negatives… Our human augmentations mitigate these false negatives by constraining the agent's solution space such that verifiers are robust」。**关键口径**:作者对增强材料的定位是让判分器稳健,而不是 spec 让代码变好。所以 25.9→8.4 混合了「agent 解决率」和「与测试期望的接口对齐」两件事,不能当成「spec 让 agent 能力提升 3 倍」。interface(签名,T3)和 requirements(T1)是一起去掉的,没有单独的消融。作者还写了「the setting without requirements is potentially interesting」,说明不带 requirements 才更接近真实工单。论文没有报告运行次数。
- **M19 HOLDS(升级为 verbatim)**:abstract 原文:「51 class-generation tasks… full docstrings (L0) to bare signatures (L3)… two-agent integration accuracy drops from 58% to 25%… single-agent baseline degrades more gracefully (89% to 56%)… consistent across two Claude models (Sonnet, Haiku) and three independent runs… restoring the full specification alone recovers the single-agent ceiling (89%), while providing conflict reports adds no measurable benefit」。复算:L0 的协调差 = 89−58 = 31pp,L3 = 56−25 = 31pp,原文给的是 25–39pp 区间 ✓。外推边界:合成的类生成任务,核心机制是**多 agent 之间共享决策**,与单 agent 仓库级 SDD 不是同一回事。
- **M21 修正(混条件 + 口径)**:作者单位确认是「Model Development Innovation, TD Bank, Toronto」。**修正**:Round 1 写「只改是否以规则清单给出规约;给规约时 30 个缺陷抓到 27 个」,把两个条件混在了一起。原文(第 117–119 行):「A tester given only a plan… with no spec, catches almost nothing (2 of 30 bugs). Given the spec as a **plain paragraph**, it catches nearly all of them (27 of 30). Splitting that same spec into a **checklist**… adds only a little more (**30 of 30**)」。所以清单条件是 30/30,27/30 是段落条件(这是一个消融)。**另外**:30 个 bug 是 48 个核心实例(8 tasks × 2 code models × 3 seeds)里**自然产生的**错误草稿(「we plant no bugs」),不是人工注入的。**两种指标不要混**:「bug 检出数(30 个)」和「代码正确率提升」是两个口径,后者原文为 +38pp(核心 8 个任务 60%→100% 即 +40pp;留出 4 个任务 +36pp;scale-up 6 个任务 +18pp);任务级 sign test 跑在 18 个任务上,p = 0.002;benchmark 共 26 个任务。边界条件逐字 ✓:「On well-specified algorithmic problems it neither helps nor hurts」。spec 平均每个核心任务 4.75 条规则(38 条 / 8 个任务)。
- **M22 修正(复算 + 基线口径,升级为 verbatim)**:Table 1(%Resolved,每个基准随机抽 100 个实例,模型为 DeepSeek-V3.2 和 Qwen-Plus):
  - DeepSeek:Lite 39 vs Claude Code 36;Verified 51 vs 46;Pro 35 vs 24(Agentless 6)
  - Qwen:Lite 28 vs 26;Verified 37 vs 33;Pro 26 vs 20

  **复算**:原文的「improves %Resolved by 2%∼29%」是相对**全部**基线的范围,上沿 29 来自 DeepSeek 在 Pro 上对 Agentless 的 35 vs 6。**相对最强基线(Claude Code),增益只有 +2 到 +11pp**(DS:+3/+5/+11;Qwen:+2/+4/+6,均值约 +5pp)。abstract 的「average improvement of 13.17%」= 18 个对比的 pp 差均值(237/18 = 13.17,复算吻合),是**百分点而不是相对百分比**,而且被弱基线拉高了。强模型:「Claude Code achieves a %Resolved score of 53%, WiseSpec further increases the score to 56%」,+3pp,n=100、单次运行,CI 必然跨零附近。Wilcoxon p<2.5×10⁻⁴ 的配对单位,文中没有说明。

## 成文提示
- 必带:SWE-Bench Pro 的消融必须带作者自己的解释:去掉 requirements 和 interface 后,测试只认特定 API,会造成假阴性;同时说明 T1 和 T3 是一并去掉的。
- 必带:TD Bank 的写法是「段落 spec 27/30、清单 30/30、只有计划无 spec 2/30(30 个自然产生的错误草稿,8 个任务)」;正确率 +38pp 和检出数是两个口径,分开写。
- 必带:WiseSpec 用「相对 Claude Code +2–11pp,强模型 +3pp」。禁止单独写「最高提升 29pp」或「平均提升 13%」。
- 最强写法(剂量-反应):「The Specification Gap 在同一组任务上逐级剥离规约,单 agent 从 89% 降到 56%;恢复完整规约即回到 89%(2 个 Claude 模型 × 3 次运行,单作者预印本)。」
