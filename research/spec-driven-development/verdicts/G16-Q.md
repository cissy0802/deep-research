In about 37% of the cases, we found a co-evolution between scenarios/fixtures and production code. This mainly happens because developers felt BDD remains quite effort-prone”。**修正**:R1 所说的“二手资料样本矛盾(50,000 vs 20 个 Ruby 项目)”不是矛盾,而是三个阶段各自的样本(采用 50,000 / 共同演化 20 / 调查 31)。新增可承重口径:共同演化只在约 37% 的情形中出现,而且规约**常与代码同时或滞后于代码**变更,这与 SDD 主张 2(spec 先于代码、保持活性)直接相关。注意“27% 使用 BDD 框架”计的是框架(含 RSpec 等),不等于做 BDD。

## 成文提示
- 必须带的限定:Binamungu 是 BDD 社区渠道招募的便利样本,“放弃”只是轶事;Zampetti 的 27% 是“用框架”而非“做 BDD”;Nagappan 是 4 对非随机比较,时间成本是管理层估计;Rafique 的效应是“小”,而且工业研究中质量收益和生产率损失**都更大**。
- 禁止的表述:“TDD 降低缺陷 40–90%”不带“四个团队、非随机、相对相似项目”;任何引用 Bissi 76%/88% 的写法;“Cucumber 作者说 BDD 失败了”(他说的是被误用为测试工具,而且他有 Cucumber Pro 的商业利益)。
- 可用的最强写法:“在 20 个用 BDD 框架的 Ruby 项目里,只有约 37% 出现规约与代码的共同演化,且规约多半与代码同时或在代码之后改动;受访开发者大多在写代码时或写完后才写测试。”以及 Fucci:“先写测试还是先写代码,这个顺序本身对质量和生产率没有重要影响,起作用的是步子小、步子匀。”
