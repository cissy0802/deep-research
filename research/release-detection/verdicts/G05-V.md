# G05-V 逐字席核验：Microsoft Gandalf（NSDI 2020）

一手原文：https://www.usenix.org/system/files/nsdi20-paper-li.pdf（2026-10-30 下载，经 pdftotext 抽文本后做规范化子串比对）。
引语核对结果：调研员给出的 11 段英文引语全部在原文中**逐字存在**（仅 "data-plane"/"dataplane" 是连字符差异）。

## 逐条判决

### CANARY:C01 — CORRECTED（单源已核，厂商自评）
- 引语逐字存在；155、92.4%、100% recall 一致。Sev0-2 的定义在原文另一处给出："no high-impact incidents, i.e., Sev0-2 outages, were caused by bad rollouts"。
- 修正 1：窗口时长。原文写的是 "8-month usage window from Jan. 2018 to Nov. 2018"，但 2018-01 到 2018-11 按日历算有 10–11 个月，**原文自身前后不一致**。成文时只能写「论文自称 8 个月窗口（2018-01 至 2018-11）」，不得自行换算。
- 修正 2：「低影响漏报不在分母里」是调研员的推论，原文没有这么说。原文只把 recall 定义为「没有 Sev0-2 事故由坏发布引起」。成文时应写成推论：「这个 recall 是代理口径，没有以人工标注的全部坏发布作分母」。
- 「检测+归因」的定性与原文一致（原文写的是 "anomaly detection and correlation analysis"）。

### CANARY:C02 — CORRECTED（单源已核；口径推论标为未验证）
- 引语逐字存在。39 filed、2 false alarms、missed 2、94.9%、99.8%、1200+ 均一致。
- 重算：precision = 37/39 = 94.87%，四舍五入为 94.9%，与原文一致。按标准定义 recall = TP/(TP+FN) = 37/(37+2) = 94.87%，也就是数值上应当**等于** precision，而不是 99.8%。
- 修正：99.8% 和 (1200−2)/1200 = 99.83% 吻合，但同样和 TN/(TN+FN) = 1159/1161 = 99.83%（NPV）以及 TN/(TN+FP) = 1159/1161（specificity）吻合。所以「分母是全部部署」只是三种可能之一。锁定表述：「按论文自己给的计数，标准 recall 为 37/39≈94.9%；论文报告的 99.8% 无法由标准 recall 定义得到，其分母未说明」。不得断言它的分母就是全部部署。

### CANARY:C03 — CORRECTED（单源已核）
- 引语逐字存在。5 分钟、3 小时、"more than half (Figure 14)" 均一致。
- 修正：「只看部署前后 1 小时」只适用于**流式层（speed layer）**。原文是 "the analysis engine in the speed layer only considers fault signals that happen 1 hour before and after each deployment"，发布 1 小时之后的潜伏故障由批处理层捕获。论断原文漏掉了「流式层」这个限定。
- 「部署时长减半以上」的对照对象是 Gandalf 之前的流程：组件级 watchdog 加大量人工邮件沟通与审批（原文 "extensive email communications were needed … to clear suspicious failure alerts and obtain approval"）。论断说它指的是部署时长、不是检测速度，这一点成立。
- 「5 分钟」是 "make decisions … end-to-end"，即决策延迟，不是从故障发生到检出的时间。

### CANARY:C04 — HOLDS（单源已核）
- 引语逐字存在，99.2% 和 0.8% 一致。原文的图注是 "percentage of issues we detected in different environments"，分母是被检出的问题，论断对分母的说明正确。
- 误删目录的例子原文为："a faulty agent update accidentally deletes an important folder … Later, a GuestOS update by customer touched that folder and triggered faults, causing Gandalf to mis-blame the GuestOS deployment"。与论断一致。
- 附注：0.8% 无法与 155 构成整数比（1/155 = 0.65%），说明 Figure 15 的分母不是 155 个关键故障。成文时不要把两个数混在一起计算。

### CANARY:C05 — CORRECTED（单源已核）
- 引语逐字存在。案例 III 原文为 "a Network Agent in Canary. OS crashed during 24 hours to 72 hours after the deployment and Gandalf issued a Sev2 alert"，根因是 NIC 固件与驱动版本冲突，与论断一致。
- 修正（案例 I 的主语）：原文是 "CRP team claimed these failures were irrelevant to CRP rollout based on their past experience. Therefore, the release manager directly requested to bypass the no-go decision"。也就是说，判断告警无关的是 CRP 团队，要求绕过 no-go 的是 **release manager**。随后 Gandalf 在 Pilot 再次给出 no-go，经深入调查确认是 CRP 的回归。原文还写到，等 Pilot 区客户报出相关问题时，hotfix 已经部署。

### DETECT:D20 — CORRECTED（单源已核）
- 引语逐字存在，数字全部一致，32 小时案例也存在（"latent issue detected more than 32 hours after the deployment"）。
- 修正：其中的「recall 99.8%」需要附上 C02 的口径警示（标准 recall 为 37/39）。「误报集中在 Stage/Canary」原文为 "most of the false alerting are issued in Stage and Canary environment"，成立。
- 来源类型应为「同行评审（Microsoft 自评）」。

### DETECT:D21 — HOLDS（单源已核）
- 引语逐字存在，环境差异的五项列举与原文一致。后半句「与 FBDetect、Teams 研究构成共性」是跨组综合，不属于本源的论断，本席不核。

### CHANGE:C11 — CORRECTED（单源已核）
- (a) 的引语逐字存在。NIC 固件/驱动案例原文为 "the network agent rollout upgraded the NIC firmware and drivers, the firmware upgrade script missed one of the hardware revisions"，成立。">32 小时"成立。
- (b) 的修正与 C01、C02 相同：「8 个月」写成论文自称；控制面 recall 需附口径警示。原文写的是 "dataplane"，与 "data-plane" 只是连字符差异，可以接受。

## 组级判决：CORRECTED
HOLDS 2（C04、D21），CORRECTED 6（C01、C02、C03、C05、D20、C11），REFUTED 0。所有引语都逐字存在，问题集中在口径解释和限定语遗漏。

## 成文锁定口径
1. 数据面：「论文自称 8 个月窗口（2018-01 至 2018-11），捕获 155 个关键故障，precision 92.4%；recall 100% 按『无 Sev0-2 事故由坏发布引起』定义，是代理口径」。
2. 控制面：「1200+ 次区域级部署，报 39 起，其中 2 起误报，漏 2 起。按标准定义 recall=37/39≈94.9%；论文报告的 99.8% 分母未说明」。不得写「recall 99.8%」而不加注。
3. 时间：「决策延迟（不是故障到检出的延迟）在流式层约 5 分钟、批处理层约 3 小时；流式层只看部署前后 1 小时的信号」。
4. 99.2% 的分母是被检出的可疑 rollout，不是全部坏 rollout，也不能与 155 互算。
5. 案例 I：「CRP 团队认为告警无关，release manager 要求绕过 no-go」。
6. 来源一律标为 Microsoft 作者自评自家生产系统。
