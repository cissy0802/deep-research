# G06-V 逐字席核验：Google CAS / SRE Workbook / Kayenta / Spinnaker judge

一手原文（2026-10-30 下载，规范化后做子串比对）：
- CAS：https://sre.google/static/pdf/canary_analysis.pdf（acmqueue 2018 年 1–2 月刊排版版）
- Workbook：https://sre.google/workbook/canarying-releases/
- Kayenta：https://cloud.google.com/blog/products/gcp/introducing-kayenta-an-open-automated-canary-analysis-tool-from-google-and-netflix（2018-04-10，署名 Nikhil Kaul、Andrew Phillips 等）
- Spinnaker judge 文档：https://spinnaker.io/docs/guides/user/canary/judge/

引语核对：全部 27 段英文引语逐字存在。唯一例外是 Workbook 中 "heavy load," 之后原文插有脚注编号 7，引语删掉了它，不影响含义。

## 逐条判决

### CANARY:C06 — HOLDS（单源已核，厂商自述）
- 「每天数十万次」是评估次数，对象包含二进制、配置和数据集变更，均与原文一致。
- 原文另有 "bad CAS-related rollouts are far less intrusive—typically resulting in a pause or a rollback"，以及「rollout 工具调用 CAS」的流程图，支持「CAS 只判定，暂停或回滚由 rollout 工具执行」。
- 「数十万」是 Google 自述，没有分母，也没有拦截数。

### CANARY:C07 — HOLDS（单源已核）
- 引语逐字存在。「忽略预期内失败」的机制原文为：coordinator "ignores results of statistical functions for predicted failures when deciding the overall verdict"，前提是 model server 预测这种失败属于系统常态。
- 「表现极差」对应原文 "behave extremely poorly"，成立。

### CANARY:C08 — HOLDS（单源已核）
- 引语逐字存在。「坏行为罕见」的假设原文为 "The high-level assumption is that bad behavior is rare."
- 注意：原文写的是 "It has experienced incidents"，没有给出数量。

### CANARY:C09 — HOLDS（单源已核）
- 三段引语逐字存在（含省略号两侧）。
- 「Google 没有、也认为难以给出可靠数字」是对原文的合理概括。原文确实没有给出任何拦截量或检出率数字。

### CANARY:C10 — CORRECTED（轻度，单源已核）
- 引语逐字存在。「完美准确配置会阻断可接受的变更」原文为 "Attempting a 'perfectly accurate' canary setup can lead to a rigid configuration, which blocks releases that have acceptable changes in behavior"，成立。
- 修正：「只用少数关键指标效果好得多」在原文中带有限定条件，原句是 "Some teams at Google have performed analysis that justifies using a large number of metrics, but unless you perform similarly detailed data analysis, using only a few key metrics yields much better results." 成文时必须保留「除非做过同等细致的数据分析」这个条件。

### CANARY:C12 — CORRECTED（轻度，单源已核）
- (a)(b)(d)(e) 逐字成立，5%×20% = 1% 的算术正确。「同一时间只跑一个 canary」原文为 "We strongly advise running only one canary deployment at a time"，成立。
- 修正 (c)：原文是 "Terminating a canary deployment after receiving just a handful of queries doesn't provide a useful signal **for systems characterized by diverse queries with varied functionality**"，并且原文紧接着说请求越同质、所需流量越少。论断漏掉了「查询多样的系统」这个限定。

### CANARY:C13 — HOLDS（单源已核）
- 两段引语逐字存在。
- 「直接支持 TTD 与 MTTR 必须分开」是推论，但与原文方向一致，可以使用。

### CANARY:C14 — CORRECTED（轻度，厂商口径）
- 三段引语逐字存在，0–100 分及 success/marginal/failure 的处置方式与原文一致（原文为 "failure triggers a roll back"）。
- 修正 1：「约 1% 流量」在原文中是举例（"for example, 1%"），不是典型配置。「通常各 3 台」原文为 "Typically three instances"，成立。
- 修正 2：「thousands of canary judgments per day」是 2018-04 时对当年年底的**预期**，论断已经标注了这一点。来源类型应写作 Google Cloud 博客（Google 与 Netflix 联合推广，属于厂商口径）。

### CANARY:C15 — CORRECTED（单源已核，开源文档）
- 引语逐字存在。High/Low 的判定条件原文为：98% 置信区间完全落在容差带之外，**并且** effect size 超过 allowedIncrease/allowedDecrease 阈值。
- 修正（机制错误）：论断说「除非配置 mustHaveData/nanStrategy=replace」。按原文的缺失数据处理表，只有 `mustHaveData: true` 会把缺失数据的指标判为 NodataFailMetric，计为失败。`nanStrategy: replace` 的结果是 "Pass (arrays have zeros)"：把缺失值补成 0 后再比较。canary 没有数据时，补 0 后通常判 Pass，同样不会拉低分数。文档的建议是 "Use nanStrategy: replace for error metrics where no data means zero errors"。
- 锁定表述：「低流量路径若在 canary 期间没有数据，默认判 Nodata，不计分；只有设 mustHaveData: true 才会计为失败；replace 会补 0，结果通常判 Pass」。
- 「未见多重比较校正说明」：在该页搜索 Bonferroni、multiple comparison 均无结果，成立，但只限于该文档页。

## 组级判决：CORRECTED
HOLDS 5（C06、C07、C08、C09、C13），CORRECTED 4（C10、C12、C14、C15），REFUTED 0。

## 成文锁定口径
1. CAS：「Google 自述每天评估数十万次生产变更（评估次数，不是拦截数）；CAS 不披露拦截量，作者明说影响难以度量，改用 near-miss 回溯」。
2. 少数关键指标更好，**除非**做过同等细致的数据分析。
3. 「请求太少就结束 canary 没有信号」只适用于查询多样的系统。
4. Kayenta：「1%」是举例；「每天数千次判定」是 2018 年的预期。
5. Spinnaker 低流量盲区：Nodata 默认不计分；只有 mustHaveData: true 才计为失败；nanStrategy=replace 补 0，通常判 Pass，不能作为补救写法。
6. 来源性质：CAS 和 Workbook 是 Google 工程师自述（acmqueue 和 SRE 书，非同行评审）。
