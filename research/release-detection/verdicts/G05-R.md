# G05 反证席（R）判决：Microsoft Gandalf

核验日期：2026-10-30。一手原文：NSDI'20 PDF（usenix.org，全文已下载并 pdftotext 逐句核对）；Azure 博客 "Advancing safe deployment with AIOps—introducing Gandalf"（页面元数据 2021-06-30，可能是站点迁移日期）。

## 搜索过的反证角度（含无结果的）
1. Gandalf 期刊扩展版或后续论文（"Gandalf follow-up"、2022–2023 Azure safe deployment AIOps precision recall）：**没找到**。没有 TOCS 或期刊扩展版，也没有更新的检出数据。
2. 独立复测或第三方评测（"Gandalf NSDI critique / independent evaluation"）：**没找到**，只有 the morning paper（acolyer 2020-02-28）的转述。
3. 同一系统的其他官方披露：Azure 博客版（已下载核对）。博客**没有给任何 precision、recall 或检出数字**，但补充了一处口径：batch 层"generally a 30-day period"，stream 与 batch 都"incrementally with five-minute intervals"。
4. 反方事件证据：Azure Front Door 2025-10-29 全球中断（YKYN-BWZ）。初步 PIR 称触发条件之一是"a software defect in the latest version of the AFD control plane"。InfoQ 二手报道称本应拦截坏部署的保护机制因 bug 被跳过。这只说明 Azure 的安全部署体系在 2025 年仍会漏，与 Gandalf（Azure Compute，2018）不是同一系统，**不能作为 Gandalf 指标的反证**，只能当"体系仍漏"的旁证。PIR 原文没有抓到（status history 页只显示 2026-09 的条目），属二手。
5. 误回滚率、canary 拦截率等更新的公开数据（2022–2026）：检索"automated canary analysis false positive rate production 2023 2024"和"bad deployments detected percentage canary"，结果**只有教程和厂商软文**（oneuptime、dev.to 上一篇无方法的"12,000 deployments"说法），没有可用数据。

## 逐条判决

### CANARY:C01 — **CORRECTED**
- 数字与引文逐字吻合（155、92.4%、100%，以及"no high-impact incidents were caused by bad rollouts"）。正文另一处把高影响事故界定为"Sev0-2 outages"，对"Sev0-2 代理"的解读成立。
- 修正：论文写"8-month usage window from Jan. 2018 to Nov. 2018"，但 1 月到 11 月按日历是 10–11 个月。论文自身不一致，成文不应写成"8 个月"而不加注。另外，"低影响漏报不在分母里"是本线推断，论文没有明说。
- 锁定表述："论文称 8 个月窗口（标注为 2018-01 至 2018-11，日历跨度与'8 个月'不符）；100% recall 的操作定义是'没有 Sev0–2 高影响事故由坏 rollout 引起'，不是对照全量标注的召回。"
- 分级：**厂商口径**（同行评审，但属自评，没有独立复测）。

### CANARY:C02 — **HOLDS**（推算部分须标"推断"）
- 39 起、2 起误报、漏 2 起，原文吻合。37/39 = 94.9% 与论文的 precision 一致。按标准定义，recall = 37/39 = 94.9%，而 (1200−2)/1200 = 99.83% 与 99.8% 吻合，所以"分母疑似全部部署"的推断在算术上成立。但论文没有给公式，**只能写"与……吻合，疑似"**，不能写成定论。
- 分级：**单源已核**（原文），口径推断为**方向存争**。

### CANARY:C03 — **CORRECTED**
- 5 分钟与 3 小时、"most catastrophic issues happen within 1 hour"、Figure 14 前后对比都吻合。Figure 14 对应的 Gandalf 之前流程，原文写的是"extensive email communications … to clear suspicious failure alerts and obtain approval"，支持"相对人工邮件审批"的说法。
- 修正：只看 ±1 小时的是**speed layer**，batch layer 分析**30 天窗口**（论文正文和 Azure 博客都写 30-day），相关性打分默认聚合 72 小时窗口。原论断"只看部署前后 1 小时"会误导读者以为 Gandalf 整体只看 1 小时。另外，"5 分钟"是每次部署的决策处理时延，不等于"坏发布到被发现"的 TTD：故障信号得先出现，案例 III 就是 24–72 小时后才出现。
- 锁定表述："speed layer 只看部署前后 1 小时的故障信号、约 5 分钟出决策；batch layer 看 30 天窗口、约 3 小时出决策。'5 分钟'是处理时延，不是端到端 TTD。"
- 分级：**单源已核**。

### CANARY:C04 — **CORRECTED**（口径冲突出自论文本身）
- §5.2 写"99.2% suspicious rollouts are blocked before reaching production"，结论段却写成"Gandalf blocked 99.2% of the bad rollouts before they enter production"。论文自己在两处用了不同的分母措辞。原论断判断"分母 = 被检出的可疑 rollout"是对的，但必须注明结论段的措辞会被误引为"拦住 99.2% 的坏发布"。
- 错误归责案例（agent 误删目录，后被错怪为 GuestOS）原文吻合。
- 分级：**单源已核**。

### CANARY:C05 — **CORRECTED**（细节）
- 三类漏检的引文吻合，案例 III 的 24–72 小时也吻合。
- 修正：案例 I 中，是 CRP 团队凭经验称失败与 CRP 无关，**由 release manager 提出绕过 no-go**（"the release manager directly requested to bypass"），不是 CRP 团队自己提出。随后 Pilot 再次 no-go，CRP 团队深入调查后确认是回归，客户在 Pilot 报问题时 hotfix 已经上线。"人会推翻正确的自动判定"这一结论成立。
- 另外，三类漏检描述的是**Gandalf 之前的组件级 watchdog**，是论文的动机陈述，不是 Gandalf 的漏检分析。
- 分级：**单源已核**。

### DETECT:D20 — **CORRECTED**
- 数字吻合；32 小时案例出自 §2 的 Figure 8（"latent issue detected more than 32 hours after the deployment"）。修正同 C03：要区分 speed layer 与 batch layer 的窗口，"约 5 分钟"不是 TTD。来源类型"PR"应写成"同行评审（自评）"。
- 分级：**厂商口径**。

### DETECT:D21 — **HOLDS**
- 引文逐字吻合（§1）。把它与 FBDetect、Teams 并列为"共性"是本线的综合，属于正当推论。分级：**单源已核**（Microsoft 一家的陈述）。若综合 FBDetect、Teams 后可升到**多源证实**，但要注意几家都是厂商自述。

### CHANGE:C11 — **CORRECTED**
- (a)(b) 的引文和数字都吻合。需要同步两处修正：一是"8 个月"与日历跨度不一致（见 C01）；二是 NIC 案例原文是"conflict between old firmware version and new driver version … firmware upgrade script missed one of the hardware revisions"，"NIC 固件/驱动升级"的概括成立。
- 分级：**厂商口径**。

## 组级判决：CORRECTED（HOLDS 2 / CORRECTED 6 / REFUTED 0）
没有找到推翻 Gandalf 数字的反证，但也**没有任何独立复测或后续更新数据**。所有指标停在 2018 年这一个窗口，出自单一来源，而且是自评。

## 成文时必须使用的锁定口径
1. 窗口写成"论文称 8 个月（标注 2018-01 至 2018-11）"，或直接写"2018 年约一年内"并加注不一致。不要单写"8 个月"。
2. 数据面"100% recall"等于"无 Sev0–2 事故归因于坏 rollout"，是代理指标；低影响漏报不可见。
3. 控制面 99.8% recall 与 (1200−2)/1200 吻合；按标准定义算是 37/39 ≈ 94.9%。写作"疑似以全部部署为分母"。
4. 99.2% 的分母是"被判可疑的 rollout"（§5.2），不要引用结论段"99.2% of the bad rollouts"的措辞。
5. "5 分钟 / 3 小时"是 speed/batch 两层的决策处理时延；speed layer 只看 ±1 小时，batch layer 看 30 天；真实 TTD 取决于故障何时显现（案例里有 24–72 小时、>32 小时）。
6. 案例 I 的绕过请求出自 release manager。
7. 全部数字只能标为"Microsoft 自评、单一窗口、无独立复测"；2025 年 AFD 事件只能当"Azure 安全部署体系仍会漏"的旁证，不能拿来反证 Gandalf 指标。
