## 搜索过的反证角度
1. Netflix 后续：找到 Netflix 技术博客 "Sequential A/B Testing Keeps the World Streaming Netflix"（Part 1/2，2024，未直接抓取正文，仅见二手摘要），以及 ERCIM News 145（2026-07-02）上 Lindon（Netflix）的署名文章。后者称"a single canary experiment may monitor hundreds of metrics simultaneously"，并说多重检验校正"unavoidable"。这段是泛论，没有明确说是 Netflix 自家的数据，但对 C16、C17 的外推是个重要限定：单指标的序贯误报控制不等于整次 canary 的误报控制。没有找到 Netflix 公开的误报率、漏报率或全量 canary 统计。
2. 论文自身的局限：Netflix 原文 Discussion 承认，计数类指标假设事件间隔分布平稳；对低频计数（"SPS for a rarely used device"）检验更慢，长时间 canary 中平稳性很可能被违反，"not clear to what extent the type I error guarantees … would degrade"。
3. Configerator 同文的量化数据：作者人工分析三个月高影响事故，16% 与配置管理相关。其中 Type III（"valid config changes exposing code bugs"）占 22%。这是 canary 漏检和误判信任的结构性来源，可以补进成文。
4. ICSE16 的反例或后续：没有找到独立复测。原文"We have been able to solve"一句在 PDF 中被截断，无下文，因此 Facebook 如何解决累积回退在原文中不可考。
5. Azure、Amazon 的拦截数字：两篇博客均无检出率或误回滚率。检索"2022–2026 年其他公司发布检测效果数据"，结果只有教程和软文。
6. 反方事件：Azure Front Door 2025-10-29 中断（初步 PIR：控制面软件缺陷产生了不兼容元数据；InfoQ 二手报道称保护机制被 bug 绕过）。说明 Azure 声称"中央策略强制"的安全部署体系仍可被绕过，只能作为旁证，PIR 原文未抓到。

## 逐条判决

### CANARY:C16 — **HOLDS**
引文逐字吻合，"upper bound on the time taken for the test to stop"也吻合。成文时补上第 1 点的限定：单检验的 I 类错误控制，不能直接推出多指标 canary 的整体误报率受控。分级：**单源已核**（同行评审，Netflix 自评）。

### CANARY:C17 — **CORRECTED**（补口径）
11.08 秒、约 65 秒、"prevented the release candidate from reaching the production environment"均吻合。
需要补两处：
- 论文宣称固定样本量（fixed-n）方法"would have taken upwards of 30 minutes or longer to detect the regression"，这是没有给出实验对比的断言，属作者口径。
- 论文明说，对低频计数指标（如冷门设备的 SPS），序贯检验同样慢，且平稳性假设可能被违反。秒级检出只适用于高事件率的核心指标。
原论断"n=2、作者挑选、不能外推"的判断正确，应保留。分级：**厂商口径**（案例为自选）。

### CANARY:C18 — **CORRECTED**
20 台到数千台的分阶段方式、CTR 判据、log spew 案例都吻合。schema 案例细节：代码错过了 release cut，"Five days later"才提交新 schema 配置。
修正：原文"automated canary tests take about ten minutes anyway"是**每次配置变更 canary 本身的耗时**（原文语境是解释提交延迟 14.5 秒为何不关键），**不是 TTD**。论断中"（TTD 量级）"应删除，或改为"canary 观测窗口约 10 分钟"。它只说明 canary 能抓到的问题会在这个窗口内被抓到，对 canary 漏掉的问题没有任何说明。分级：**单源已核**。

### CANARY:C19 — **HOLDS**（补细节）
引文吻合。(b) 中工程师是"immediately reverting"，原文把它归为"valid config change exposing code bugs"类，这一类占配置相关高影响事故的 22%（同文表格）。分级：**单源已核**。

### CANARY:C21 — **HOLDS**
引文吻合。早晨企业用户、晚上游戏用户、长期 VM 创建这三个例子都有原文出处；紧急加速的条件也有原文（"accelerate it when certain emergency conditions are met. For example, to release a security update"）。另外，原文说全球服务"cannot take the approach of progressively deploying"时，也有自己的一套渐进做法。分级：**厂商口径**。补充锁定：2025-10 的 AFD 事件说明，强制策略本身可能因软件缺陷失效（二手来源，只能作旁证）。

### CANARY:C25 — **HOLDS**（补措辞）
斜率 0.0004、0.0013、0.0061 及原文吻合，2009-01 至 2010-07 用热修复做代理、"at the expense of some productivity"也吻合。原文据此提出的 Observation 3 是"critical issues … almost constant regardless of the number of deployments"。论断中"相关非因果、未单独度量 canary"的限定正确。另外，作者中 Savor 是 Facebook 员工（fb.com 邮箱），Gentili 来自 OANDA。分级：**单源已核**。

### CANARY:C26 — **HOLDS**
"hypothetical"、0.05%×100 次/周、一年 +260%，均与原文吻合（52×100×0.05% = 260%，线性累加）。"MDE 以下永远看不见"是本线推论，要标为推论。原文没有给出 Facebook 的解决办法（该句在原文中截断）。G08 的 FBDetect 和 TOCS 用跨版本长期检测处理渐变回归，可作为同一推论的佐证。分级：**单源已核**（假设算例），推论部分为**方向存争**，与 FBDetect 合看可升级。

### CHANGE:C10 — **HOLDS**
内容与 C18、C19 重复，引文吻合。"URL: 同 C09"指代不明，应改为 SOSP'15 Configerator 的 URL。分级：**单源已核**。

### CHANGE:C21 — **CORRECTED**
引文全部吻合：至少 1 小时、12 小时、2–4 小时，"about four or five business days"，"at least 100 requests to the Create API"，one-box 告警的局限，以及 off-hours。
修正：论断把 bake time 解读为"坏发布影响可能多晚才显现的厂商经验上界（小时到天级）"，这是**过度引申**。原文把 bake time 写成风险权衡的设计参数（"balance the risk of causing a broader impact … too quickly"），并且说大型或关键服务"even more conservative"。原文既没有说坏发布影响会在这些时间内显现，也没有提供任何实测分布。
修正后的表述：Amazon 的典型流水线在每个生产阶段后设 1 小时到 12 小时不等的 bake time，并设最少请求数门槛，用来捕捉"slow burning"影响。这反映了厂商认为慢燃问题是小时级现象的**设计判断**，不是实测的显现时间上界。
分级：**厂商口径**。

## 组级判决：CORRECTED（HOLDS 6 / CORRECTED 3 / REFUTED 0）

## 成文时必须使用的锁定口径
1. Netflix 的 11 秒和 65 秒来自 2 个自选的高流量核心指标案例；低频计数指标检出慢，且平稳性假设可能失效；"fixed-n 需 30 分钟以上"是作者断言。
2. 单指标序贯检验控制的是单检验的 I 类错误；一次 canary 可能同时监控上百个指标（Lindon 2026，泛论），整次 canary 的误报需要多重检验校正。
3. Facebook 的"约 10 分钟"是 canary 观测窗口，不是 TTD。
4. Facebook 配置相关事故占三个月高影响事故的 16%，其中 22% 是"合法配置暴露代码 bug"。这是 canary 误判信任问题的来源（SOSP'15，单一窗口）。
5. Amazon bake time 是设计参数，不是"影响多晚显现"的实测上界。
6. ICSE16 的斜率只表示相关；0.05%/260% 是假设算例。
7. Azure 和 Amazon 都没有公开检出率或误回滚率。
