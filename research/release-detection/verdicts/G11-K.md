# G11 口径席（K）判决

核验方式：arXiv 全文（2404.16887 Walmart AIDR、2305.18985 AnoFusion、2507.09315 SCELM）以 pdftotext 逐段核对；SCWarn 摘要与作者单位取自 ESEC/FSE 2021 官方页（WebFetch）。SCWarn 正文未读。

## CHANGE:C28 — CORRECTED（证据分级：单源已核，仅摘要层）
- 50.4%、0.95 F1、MTTD 降 20.4%–60.7% 与摘要逐字吻合。
- 「已知坏变更数据集上与基线方法比较」是**推断**。摘要只写 "two datasets with various bad software changes" 和 "significantly outperforms all the compared approaches"，没说明 MTTD 降幅相对的是什么，也没说明两个数据集是否都来自该银行。成文应写「摘要未说明 MTTD 对照对象（推测为对比算法）」。
- 漏标利益方：作者包括 **BizSeer**（AIOps 商业公司，3 人）和广发银行（3 人）；Dan Pei 同时在清华。来源类型应写「学术 + AIOps 厂商 + 数据方银行」，不只是「学术 + 企业数据」。
- 摘要还提到 "success stories ... from the practical usage"，但没有给线上数字。

## DETECT:D22 — CORRECTED（证据分级：单源已核；厂商自评，workshop）
- **63% 的分母不是 Walmart 全部重大事故。** Table 3 的四个案例客户合计 4+3+3+27=37 / 4+3+3+48=58 = **63.8%**，与摘要的 63% 对上。所以 63% 是 **4 个案例客户的 58 起事故**上的覆盖率，而且 48 起来自同一个 Operations 团队，权重被它主导。成文必须写明这个分母。
- 「MTTD 减少 7 分钟以上」：各案例的数值不同。Pricing & Delivery 约 7 分钟，Payments 14 分钟，Operations 7.2 分钟。摘要里的「>7 分钟」是案例的下限式概括，不是全量平均。论文没给基线 MTTD（论断这点正确）。
- 内部不一致：摘要写 "more than 25 ... teams"，正文写 "around 30"。正文还写 "alerted early for 37 major incidents"，37 正好等于 Table 3 检出数之和。
- XGBoost 96%/10% 和 ARIMA 98%/53% 是**离线模型选型实验**的数字，不是生产告警的 precision/recall。
- 其余数字（56% 27/48、7.2 分钟、噪声降 91%、3000+ 模型、3 个月/90 天）均吻合。

## DETECT:D23 — CORRECTED（证据分级：方向存争）
- 数字吻合：AnoFusion Table 中 SCWarn 在 D1/D2 上 P/R/F1 为 0.547/0.425/0.447 和 0.633/0.891/0.734。
- **任务口径不同。** AnoFusion 评的是**微服务实例故障检测**（failure detection），不是**坏变更识别**。SCWarn 在那里被当作通用多模态异常检测基线复用：D1（GAIA）有 trace，SCWarn 不用 trace，作者原文也拿这一点解释 SCWarn 在 D1 上为何差。所以这组数字说明的是「跨任务、跨数据迁移时分数大跌」，不是「SCWarn 原口径不可复现」。
- **利益方标注错误。** AnoFusion 的作者包括 Dan Pei，他也是 SCWarn 的通讯作者，两篇出自同一学术圈。「竞品方法作者」不准确，更准确的说法是「同一团队后续方法论文中的基线」。新方法论文压低基线分数的动机仍然存在。
- 数据：D1 是 GAIA（CloudWise 开源，注入故障）；D2 是某商业银行微服务系统，由运维人工注入故障，标签来自故障报告。
- 修正表述：SCWarn 在自家坏变更数据上报 F1 0.95；在后续同团队论文的实例故障检测任务（注入故障）中作为基线，F1 只有 0.447/0.734。这说明它换任务换数据后分数不稳，不能当作原结果不可复现的证据。

## CANARY:C27 — CORRECTED（证据分级：单源已核，仅摘要层）
- 与 C28 是同一来源的重复条目，成文时应合并。
- 「两个数据集含注入/历史坏变更」在摘要中**找不到依据**，摘要只写 "various bad software changes"，应删除或标为未验证。
- 「MTTD 降幅相对其他算法基线」同样是推断，见 C28。
- 「单一机构样本」只对 50.4% 的实证研究成立。评测数据集的来源摘要没有说明。

## CANARY:C28 — CORRECTED（证据分级：未验证到弱单源；预印本、作者自评）
- 数字吻合：ECD F1 1.000/0.942/0.925，五个基线的平均 F1 0.8935/0.888/0.868/0.869/0.8685，「90% time to resolution」、OCE 反馈，原文均在。
- **这份预印本是未完成稿，警示应升级。** 实验设置一节只有提纲式条目（"Datasets: yunzhanghu, kontrast, bytedance / Baseline Approach / Evaluation Metric / Deployment: environment"）。Fig.1 的图注是 ACM 模板占位符 "Seattle Mariners at Spring Training, 2010"。正文残留 "Figure 11 (to be added ...)" 和 "Make sure to enter the correct conference title"。数据集规模、评测指标定义、基线怎么跑，**全都没有给**。数据集名称与 D1–D3 的对应关系也只能推断。
- 「抽 10% 只有 2 个案例」出自 RAG 历史经验比例的消融实验（"Historical cases are randomly sampled ... from datasets D1 and D2"），指的是 D1 历史案例库的规模。推知 D1 约 20 例只是近似，不能当测试集规模。
- 线上部署：原文写部署在 "a large-scale SaaS microservices infrastructure"，运行 11 个多月，每周监控数千次变更。「检测几乎所有错误变更」「>95% F1」「约 75% 定位准确率」都是 **OCE 反馈**，没有分母和评判协议。「time to resolution 降 90%」是相对 "traditional manual analysis" 的 MTTR 类指标（论断这点正确），不能当检测速度证据。
- 作者包括腾讯（Bo Wu）。论断写的「南开/清华/腾讯」吻合。

## 组级判决：CORRECTED（HOLDS 0 / CORRECTED 5 / REFUTED 0）
本组最严重的问题是 Walmart 63% 的分母被读成全量事故，实际只是 4 个案例客户的 58 起；其次是 SCWarn「复现失败」是跨任务比较，以及 SCELM 是未完成的草稿。

### 成文时必须使用的锁定口径
1. Walmart：「4 个案例客户 58 起重大事故中覆盖 37 起（63%），其中 48 起来自 Operations 团队（覆盖 56%）」；MTTD 各案例减 7–14 分钟，**无基线**；作者为 Walmart 自评。
2. SCWarn 0.95 F1 和 MTTD 20.4–60.7%：作者自评（含 BizSeer 厂商作者）、离线数据集、对照对象未披露。50.4% 的分母是单一银行研究窗口内的事故。
3. AnoFusion 中的 SCWarn 分数：「实例故障检测任务上的基线分数（注入故障）」，不叫「复现」。
4. SCELM：「未完成预印本，评测设置缺失」，证据分级降到「未验证」；90% 是 time to resolution，不是 TTD。
5. 本组没有任何一条是独立第三方评测的线上检测时间。
