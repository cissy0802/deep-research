# G14-R 反证席判决:AI SRE 厂商宣称与「LLM 不进检测段」

镜头:R。日期 2026-10-30。

## 搜索记录(含无果角度)
- AWS GA 博客(WebFetch)+ **AWS DevOps Agent AI Service Card**(docs.aws.amazon.com,截至 2026-09-30)全文 → 找到了厂商自己的评测方法学。
- 「AWS DevOps Agent 独立评测」:没有系统性的第三方评测。只找到一篇上手测试(AWS Fundamentals newsletter,至少 2 个 IAM 配置错误场景,1 对 1 错)和一篇 stakpak 评论(未细读)。
- Azure SRE Agent:GA 帖正文抓不到,数字经检索摘要和 GitHub 社区仓库交叉印证。另外用 curl 抓到 The New Stack 2026-09-15 的 **Microsoft 赞助稿**,称内部已处理「1.8 million+ incidents」,并提到 "support proactive detection"。
- Datadog 两篇博客用 WebFetch 核对。没搜到 Bits AI SRE 的第三方或客户独立准确率报告。
- Traversal、Cleric 用 WebFetch 核对;Resolve 的 Salesforce 客户页和首页用 curl 抓 HTML 核对(数字在 RSC 数据里,WebFetch 读不到)。
- Grafana、incident.io、Google Cloud Assist 文档用 WebFetch 核对;The New Stack(PagerDuty 稿)用 curl 核对了赞助标签。
- 「LLM 在告警之前检测回归」:只找到厂商营销(Metoro、NeuBird「提前 30–60 分钟」、Cleric、Azure 的 "proactive detection"),**没有任何检出率、误报率或提前量的测量**。
- Traversal、Resolve、Cleric 的客户独立报告:**没有**。

## 逐条判决

### RCA:L19 — CORRECTED(厂商口径)
- 核实:GA 博客 2026-03-31,"up to 75% lower MTTR, 80% faster investigations, and 94% root cause accuracy… 3–5x";Zenchef 案例「20–30 分钟,对比估计的 1–2 小时」。
- 修正:「94% 没说明谁判定」只对 GA 博客成立。AWS 自己的 **Service Card** 披露了内部评测方法:在真实 AWS 基础设施上**注入已知故障**,由 **LLM 语义判官**比对人工整理的 ground truth,定期人工抽查;按 Pass@1、Pass@3、Pass^3 报告,带 95% 置信区间。发布门槛是「根因 Pass@1 ≥ 95%」,但**确切结果不公开**("tracked internally")。GA 博客里的 94% 被归为「预览客户与伙伴报告」,与 Service Card 的内部指标不是同一个口径。
- 反证:第三方上手测试中,AWS DevOps Agent 在环境变量与 IAM 策略不匹配的场景下给出了**错误根因**,而且建议的修复会引出另一个错误。Service Card 也把「根因识别错误」列为影响最大的错误类型,并说明产品**不提供置信度分数**。

### RCA:L20 — HOLDS(多源证实,官方一手),范围需要标注
- 证实来源:AWS Service Card 的示例工作流第一步就是 "a CloudWatch alarm fires",最佳实践中要求「配置合适阈值的告警来触发调查」;Datadog 写的是 "the moment they trigger";Google Cloud Assist 是人工点 Investigate 或从告警/日志入口发起;Grafana 是告警触发后并行运行。
- 补充(缩窄):「LLM 不进检测段」对 AWS、Datadog、Google 成立。但 Datadog 有 Preview 功能「无需 monitor 触发即可调查」;Azure SRE Agent 的赞助稿称 "support proactive detection";Cleric 和 Metoro 称会检查每次变更或每次 rollout。这些都是**进入检测段的宣称,但没有测量**。成文时写「主流产品由告警触发;少数厂商宣称主动检测,但没有公开检出率、误报率或提前量」,不要写「没有厂商在做检测」。

### RCA:L21 — CORRECTED(厂商口径)
- 1,300+、35,000+、20,000+ 小时、2026-03-10 经检索交叉印证。另一篇 Microsoft 博客写的是 50,000+ 小时(9 个月),本来就不一致。
- 更新:2026-09-15 Microsoft 赞助的 The New Stack 稿称 "handled more than **1.8 million** incidents inside Microsoft"。从「mitigated 3.5 万」变成「handled 180 万」,说明计数口径在变:**handled 不等于 mitigated**。仍然没有准确率、分母或分段数据。

### RCA:L22 — HOLDS(厂商口径),补充
- 原文和日期(01-12、03-05)已核实,正文没有准确率数字。补充:2026-01 那篇博客另写了 "decrease time to resolution by up to 95%",这是 MTTR 类的 "up to",同样不能当检测或定位证据。

### RCA:L23 — HOLDS(厂商口径)
- 原文已核实,页面没有日期,准确率口径未定义。

### RCA:L24 — CORRECTED(厂商口径)
- 用 curl 核实了 ~60%、~70%、~30%、"5x faster MTTR"、"up to 80%"。客户页日期是 2026-09-20。
- 修正:「MTTR 的更大降幅**必然**来自其他因素」推论过强。同一页面把「告警分诊快约 70%」也归功于 Resolve AI,而且产品宣称参与协调和沟通。所以 MTTR 降幅超出调查时间降幅的部分,可能来自 AI 在分诊和协调上的作用,也可能来自非 AI 因素,**无法区分**。应写成「MTTR 是多段混合指标,不能归因到定位或检测」。

### RCA:L25 — HOLDS(厂商口径)
- 用 WebFetch 再次核实了脚注:58% 是 Cleric 自己判定的 "No action needed"(2026-05-20 至 10-15);51% 由 Cleric 的 "resolution monitor" 判定(Q3 2026);4.08/5 来自可选评分(09-15 至 10-14,83% 是 4–5 星);变更检查那句原文一致;没有检出率、误报率或 TTD。三个指标的统计窗口各不相同,原论断笼统写成「5–10 月」不够精确。

### RCA:L26 — HOLDS(厂商口径,n=1)
- 2026-01-29;3.5x = 28/8 分钟;AI 是在告警触发、on-call 确认之后在后台并行启动的。

### RCA:L27 — CORRECTED(厂商口径)
- 原文已核实,另有一个目标值:精度 > 80%、召回约 60%。
- 修正:「大多数客户自测准确率背后的样本量可能极小」是推论,这篇指南是**建议**,不是对实际客户做法的观察。应写成「厂商给买家的回放建议样本只有 5–10 个事件,这个量级不足以估计准确率」。

### RCA:L28 — HOLDS(官方一手)
- 原文和 2026-04-10 的 Premium Support 限制已核实;没有准确率。补充:调查由人工从告警、日志或控制台入口发起,支持 L20。

### RCA:L29 — HOLDS(媒体转述,厂商赞助)
- 用 curl 核实:作者 Mandi Walls,标签 "sponsor-pagerduty"、"sponsored":"yes",日期 2026-04-21,59%/37% 原句一致。补充:文章**标题**把 37% 写成「只有 37% 的开发者信任 AI 做事故响应」,而正文其实是「同意 AI 能把停机改善 20% 以上」,标题本身就偷换了口径。原论断提醒「这不是信任问题」是对的。

## 组级判决:CORRECTED(HOLDS 7 / CORRECTED 4 / REFUTED 0)
最重要的发现:AWS Service Card 披露了厂商内部评测方法(故障注入 + LLM 判官 + Pass@1 ≥ 95% 发布门槛,结果不公开),第三方上手测试也出现了错误根因。「LLM 不进检测段」对主流产品多源成立,但已有厂商宣称主动检测,只是没有测量。

## 成文锁定口径
1. AWS 94%:「预览客户与伙伴报告,up to,未给分母」;厂商内部评测是故障注入场景加 LLM 判官,目标 Pass@1 ≥ 95%,结果不公开;没有独立评测,一次第三方上手测试出现了错误根因。
2. 检测段:AWS、Datadog、Google、Grafana 由告警或人工触发调查(多源一手证实);Azure "proactive detection"、Cleric 变更检查、Metoro rollout 验证属于「宣称进入检测段」,没有公开的检出率、误报率或提前量。
3. Azure:3.5 万 "mitigated"(2026-03)和 180 万 "handled"(2026-09,赞助稿)不是同一口径,都不是准确率。
4. Resolve:MTTR −60%、调查时间 −30%、分诊快 70%,MTTR 是混合指标,不做归因。
5. The New Stack 59%/37%:PagerDuty 赞助稿,讲的是对改善幅度的预期,不是信任。
