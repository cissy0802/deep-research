## 总判决

R3 **不能**以「发布后检测在大厂确实有效」承重。降级后可承重的结论：**在拥有超大流量与成熟遥测的大厂，作者自报这类系统在其自选真值下漏报极少；但精度只有约 70%（FBDetect 可核子集），检出不等于拦下，TTD 基本没有报告。** 三篇都是系统所有者自评，没有一篇做推断统计，没有一篇给出独立真值。

## 一、逐数字判决与重算

### Microsoft Gandalf（NSDI'20；11 位作者中 10 位来自 Microsoft Azure / MSR）

| 原数字 | 重算 / 核查 | 判决 |
|---|---|---|
| 控制面 precision 94.9% | 39 告警、2 误报 → 37/39 = **94.9%** ✓。Wilson 95% CI **[83.1%, 98.6%]** | **降级**：数字可复现，但 n=39，必须附 CI |
| 控制面 recall 99.8% | 标准 recall = TP/(TP+FN) = 37/(37+2) = **94.9%**，**不是 99.8%**。99.8% ≈ 1198/1200（= 1 − 漏报/总部署数），也约等于 specificity 1159/1161 = 99.83%。分母被换成了「全部 1200+ 部署」，把大量本来无问题的部署算成命中。因为 FP = FN = 2，precision 与 recall 恰好都是 94.9% | **否决** 99.8% 作为 recall；锁定 recall = **94.9%（37/39，CI 83–99%）** |
| 数据面 155 关键故障、precision 92.4% | 155 无论作分子（155/x）还是作分母（k/155），都凑不出四舍五入为 92.4% 的整数比（155/168 = 92.3%，143/155 = 92.3%，144/155 = 92.9%）。告警总数和 FP 数都没有报。很可能是按环境加权或另有口径（Fig.16 分环境），但文中没有说明 | **降级**：只能引作「作者报告约 92%」，不可重算，不得当精确值 |
| 数据面 recall 100% | 定义原文为「没有高影响事故（Sev0-2）由坏发布引起」，是**代理真值**：漏报只有升级到 Sev0-2 才计入。Sev3+ 及未被归因的漏报都不进分母。分母未知，无法给 CI | **否决** 作为 recall 数字；可改述为「观察期内作者未记录到由坏发布引起的 Sev0-2」 |
| 「8 个月窗口，2018-01 至 2018-11」 | 日历上是 10–11 个月，**文内自相矛盾** | 记录为瑕疵，引用时写「2018 年内约 8–11 个月」 |
| 99.2% 坏发布在进生产前被拦 | 分母是**被 Gandalf 检出的**问题（Fig.15「issues we detected」），是以检出为条件的比例，不是全部坏发布的拦截率 | **降级**：只能说「已检出的问题中 99.2% 发生在生产前阶段」 |
| ~5 分钟 go/no-go | 原文是 speed layer「end-to-end decision」耗时，即流水线延迟；实时引擎本身看部署前后 1 小时窗口，batch 层约 3 小时，潜伏故障为 24–72 小时（Case III） | **否决** 当作 TTD；锁定为「决策流水线延迟约 5 分钟；检测窗口为小时级到天级」 |

真值构造：告警的 TP/FP 由组件团队反馈判定（人工标注，但标注者就是被告警方，且没有报告标注一致性）；FN 只来自事后事故（代理指标）。
推断统计：无。没有 CI、没有基线对比实验（ablation 在同一份内部标注上做），也没有前后对照的统计检验（Fig.14 的部署时长是归一化后的条形图）。
检出 ≠ 拦下：Case I 中 release manager **手动 bypass 了 no-go**，直到 Pilot 再次报警才被采信。自动 stop 存在，但人可以覆盖，而覆盖率没有报告。

### Meta FBDetect（SOSP'24；15 位作者全部挂 Meta，其中 2 位兼 OSU）

| 原数字 | 重算 / 核查 | 判决 |
|---|---|---|
| 0.005% 阈值 | 是 FrontFaaS（small）配置下的 **gCPU 绝对差**，前提是 50 万+ 服务器、子程序级栈采样，分析窗 4h + 延展窗 6h。同一篇论文里，16 台服务器的 Invoicer 只能做到 **0.5%**（还要每秒采样、窗口 1 天） | **降级**：只在超大 fleet 的 CPU 效率回归上成立；论文自身数据**反证**它能外推到小服务 |
| 396 万 change point 滤掉 99.7% | 99.7% 只是 went-away detector **一步**的过滤率（1/365 → 99.73%）。全流程是 1/18857 → **99.995%**，3.96M/18857 ≈ 210，加上 long-term 约 12 条，与 217 吻合。这是降噪比例，不是准确率 | **降级**：只能当「降噪量级」引用，不得当作 precision 或 accuracy |
| 217 报告，确认子集 49 真 / 21 假 | 可核 precision = 49/70 = **70.0%**，Wilson CI **[58.5%, 79.5%]**。确认率只有 70/217 = 32%，选择偏倚未知。在全量 217 上取极值：全部未确认为真 → 90.3%，全部未确认为假 → 22.6%。EGADS 对比集里独立的人工复核给出 76/107 = **71.0%**（CI 62–79%），与 70% 互相印证 | **通过**（作为「约 70% precision」）；**否决**任何「近乎零误报」的表述 |
| 「每 13 年一次误报」 | 是**按人均摊**的指标：217 × 21/70 ≈ 65 条误报/月 ≈ 780 条/年，反推约 1 万名开发者。它衡量的是单个开发者的打扰频率，不是检测器的误报率。分母越大的组织数字越好看，是规模的产物 | **否决** 作为检测质量证据 |
| 「以 4 起事故作漏报真值」 | 2023 全年 FrontFaaS 共 4 起性能事故：2 起**检出但开发者没有及时处理**，1 起指标没有接入（作者算作「不该它管」），1 起与变更无关。有效 recall = 2/2，Wilson CI **[34%, 100%]**（Clopper-Pearson 下界 15.8%）。如果把未接入那起算进分母，就是 2/3。作者自己承认：0.005% 级别的漏报连开发者也发现不了，所以真值**结构性地**不完整 | **否决** 作为 recall 证据；**反而是「检出 ≠ 拦下」的正面证据**：可归因的 2 起都检出了，也都没拦住 |
| EGADS 对比中 FNR = 0 | 原文写的是「we assume its false negative rate is zero」，是**假设，不是测量** | **否决** |
| 三年全站只找到 1 起 FBDetect 漏报事故 | 由作者自行检索，没有给出检索方法 | **降级**（轶事级） |

适用域警告：FBDetect 检测的是**资源效率回归**（CPU、吞吐），主要后果是浪费服务器，不是用户可见的故障或坏发布。拿它支撑「坏发布上线后多快被发现」本身就有题目错配。
TTD：没有测量分布。结构下限可以从 Table 1 读出：大回归（3%）是 30 分钟重跑 + 3 小时分析窗；0.005% 是 2 小时重跑 + 4 小时分析 + 6 小时延展，量级约 10 小时以上；AdServing long 窗口长达 9 天。

### Walmart AIDR（ASPLOS'24 AIOps workshop，arXiv 2404.16887；作者全部来自 Walmart Global Tech）

| 原数字 | 核查 | 判决 |
|---|---|---|
| MTTD 减少 7 分钟以上 | 正文中 7 分钟只对应 pricing/delivery 一个子案例（payment 是 14 分钟，另有一处写 7.2 分钟）。没有报事故数 n、基线 MTTD 绝对值、方差，也没有对照设计；验证窗口约 90 天。系统是**通用异常检测**，不是发布检测，「major incidents」也不限于发布引起的事故。摘要说 25 个团队，正文说约 30 个，前后不一致 | **否决** 作为发布检测证据；最多作为「大厂 AIOps 自报 MTTD 缩短为分钟级」的轶事 |

## 二、横向审计要点

1. **真值**：Gandalf 和 FBDetect 的 FN 真值都依赖「事后升级成事故」。这是代理指标，会系统性漏掉没造成事故的漏报，recall 天然偏高。FP 由被告警的团队标注，没有一致性检验。
2. **分母**：Gandalf 控制面 recall 换了分母（99.8%）；FBDetect 用开发者人数摊薄误报（13 年）；Gandalf 的 99.2% 以检出为条件。三处都是分母操作。
3. **推断统计**：三篇都没有任何 CI 或检验。小样本（39、70、2、4）配百分比，精度被夸大了。
4. **时间窗与代表性**：Gandalf 只有 2018 年一段（而且月数自相矛盾），FBDetect 的 FP 只有 1 个月、FN 只有 2023 年一年，都只针对 FrontFaaS（作者挑它的理由是「人工标注最完整」）；Walmart 约 90 天。都是自选窗口，没有说明窗口怎么选的。
5. **利益冲突**：三篇都是系统所有者写自家生产系统，同时又是论文卖点。没有外部复核，数据不可得，结果无法复现。
6. **外推到中小组织**：作用机制依赖海量样本压低方差（FBDetect 明说 0.005% 要靠子程序级采样乘以 50 万台）和稳定基线（10 天历史窗口、需处理季节性）。论文自带的反例：16 台的 Invoicer 只能做到 0.5%，窗口要 1 天。中小组织流量小、基线噪声大、发布更不规律，阈值和检出延迟都会差 1–3 个数量级。**不可外推。**
7. **检出 ≠ 拦下**：Gandalf Case I 被人工 bypass；FBDetect 2/2 起「检出」事故都没有被及时处理；Walmart 只说「触发至少 12 次代码变更/回退」，没有分母。
8. **TTD**：三篇都没有报告「从坏发布生效到检出」的分布。Gandalf 的 5 分钟是流水线延迟，FBDetect 的窗口是小时到天，Walmart 是相对改进，没有绝对值。

## 三、成文可以怎么说 / 不能怎么说

**可以说：**
- 「Microsoft 的 Gandalf 自报：在约 1200 次控制面区域级部署中发出 39 次 no-go，其中 2 次误报、另漏掉 2 个问题，precision 与 recall 按标准定义都约为 95%（n=39，95% CI 约 83–99%）。」
- 「Meta 的 FBDetect 在一个月内报告 217 条回归，开发者明确确认的 70 条中 49 条为真，precision 约 70%；它的强项是降噪，把数百万变化点压到数百条，而不是零误报。」
- 「两家系统的漏报评估都以『事后成了事故』为真值，这种口径会低估漏报。」
- 「即便在大厂，检出也不等于拦下：Gandalf 的 no-go 曾被人工绕过；FBDetect 检出的 2 起事故都没有被及时处理。」
- 「FBDetect 的 0.005% 灵敏度依赖 50 万台规模的采样；同一系统在 16 台服务器的服务上只能做到 0.5%。」

**不能说：**
- ✗「Gandalf 控制面 recall 99.8%」（分母错误，正确值 94.9%）
- ✗「Gandalf 数据面 recall 100% / 零漏报」（代理真值，分母未知）
- ✗「FBDetect 每 13 年才一次误报」或任何「几乎无误报」的说法
- ✗「FBDetect 过滤掉 99.7% 的误报」（那是单步降噪率，不是准确率）
- ✗「Gandalf 5 分钟发现坏发布」（是决策延迟，不是 TTD）
- ✗「大厂发布后检测有效 → 中小团队照搬也有效」
- ✗ 把 Walmart「MTTD −7 分钟」当作发布检测的证据

## 四、锁定数字（重算后）

| 项 | 锁定值 |
|---|---|
| Gandalf 控制面 precision | 37/39 = 94.9%（Wilson 95% CI 83.1–98.6%） |
| Gandalf 控制面 recall | 37/39 = 94.9%（同上 CI）；**99.8% 作废** |
| Gandalf 控制面「未漏比例」 | ≈1198/1200 = 99.8%（只可标注为 1 − FN/总部署，不叫 recall） |
| Gandalf 数据面 precision | 作者报 92.4%，**不可从 155 重算**，引用时写「约 92%（未披露分母）」 |
| Gandalf 决策延迟 | speed layer 约 5 分钟 / batch 约 3 小时；检测窗口 1 小时到 72 小时 |
| FBDetect precision（确认子集） | 49/70 = 70.0%（CI 58.5–79.5%）；全量极值界 22.6–90.3%；独立复核集 76/107 = 71.0% |
| FBDetect 降噪 | 全流程 1/18857 ≈ 99.995%；went-away 单步 99.73% |
| FBDetect 漏报评估 | 可归因 n=2，2/2 检出（CI 34–100%），**0/2 被及时拦下** |
| FBDetect 0.005% 适用条件 | 50 万+ 台，检测窗口约 10 小时以上；16 台服务对应 0.5% |
| Walmart MTTD | 子案例 −7 分钟（pricing/delivery）、−14 分钟（payment）；n、基线、方差均未报；非发布专用 |
